# Agent 回复引用开发方案

- 状态：第一阶段已开发，待浏览器验收
- 决策姿态：低成本保留选项
- 首次验收点：完成回复的引用按钮、输入区引用 chip、短指纹发送
- 复核触发：第一阶段用户验收、同步官方 WebUI，或出现多引用、跨客户端精确回跳需求

## 原始需求留档

记录日期：2026-08-20。

> 如果给会话中 agent的回复结果底部增加一个引用对话的功能，你觉得应该如何设计，需要开发成一个对应的pi插件吗

浏览器批注目标：“复制”。

> 添加到它的右侧

> 我不希望应用的文本直接出现在输入框中，而是设计成跟文件引用类似的样式，换个图标，呈现缩略文字

> 重点是要优化上下文，要符合 pi agent 的极简节省的设计语言和节省 token 的优雅压缩设计

需求落点：已完成的 Agent 回复底部增加“引用”操作；点击后在输入区显示类似文件附件的引用 chip，正文输入框只保留用户正在编写的内容。引用必须帮助模型定位原回复，但不得默认复制整段回复。

## 结论

采用“结构化界面、压缩文本传输”：

- WebUI 用独立引用 chip 表达草稿状态；
- 发送时才把引用序列化为当前用户消息开头的一行短标记；
- 原回复仍在有效上下文时只发送短指纹；
- 原回复位于最近一次上下文压缩之前时，才发送有界的首尾摘录；
- 不修改历史 assistant 消息，不把引用写入系统提示词；
- 不新增用户需要安装或管理的 pi 插件；
- 第一阶段不新增私有消息类型或 `quote` wire part。

引用属于 Pi Code 的浏览器交互，不是独立 Agent 能力。pi 扩展可以改写输入或上下文，但不能自然拥有冻结版 WebUI 的消息按钮。把引用做成插件会同时引入扩展安装、WebUI 渲染和自定义消息翻译三类耦合，当前需求不足以支撑这笔维护成本。

## 产品行为

### 回复底部

- 仅在已经完成且包含最终文本的 assistant 回复上显示引用按钮。
- 按钮位于“复制”右侧，使用引用或回复语义图标，与现有“从此处分叉”图标明确区分。
- 按钮尺寸、颜色、悬浮、键盘焦点和触摸热区与相邻消息操作一致。
- 提示文案使用“引用这条回复” / `Quote this reply`。
- 同一轮由多段连续 assistant 消息组成时，引用范围与现有“复制”一致：只收集连续回复中的最终文本，不包含 thinking、工具输入输出、媒体卡片和耗时。

### 输入区

引用 chip 复用文件附件的密度和布局，不复用文件语义：

```text
↩  看完了，这是个挺有意思的个人情报自动化项目……  ×
```

- 使用独立引用图标；
- 单行显示规范化后的缩略文字，溢出省略；
- chip 位于输入框卡片内部，尺寸与文件附件一致，图标使用中性色；
- `×` 只移除引用，不清空正文和其他附件；
- 点击引用后自动聚焦正文，光标保持在用户草稿末尾；
- 已有草稿不得被覆盖或移动；
- 第一阶段只允许一条引用，再次引用时替换原引用；
- 引用源失效检测留到第二阶段；第一阶段仅保存有界摘录，不因源消息离开可见 DOM 而误判失效；
- 引用状态按会话保存，不随工作区其他会话串用。

静止界面中的 textarea 只包含用户可编辑的正文。引用标记仅在提交事件的同一同步任务中写入，由官方提交处理器读取；浏览器绘制前即进入原生清空或失败恢复路径，不能产生可见闪现。

### 发送后

- 用户消息仍以 pi 原生文本消息保存；
- WebUI 识别消息开头的引用标记，将它折叠成只读引用 chip，正文继续按原规则显示；
- pi CLI 或其他未适配客户端看到的是一行短标记和正文，仍可理解，不依赖私有二进制数据；
- 第一阶段不承诺刷新后的精确点击回跳；只保留缩略文字展示。确有跨客户端精确引用需求后再评估结构化协议。

## 上下文压缩约定

### 热路径：原回复仍在有效上下文

从原回复第一个非空正文段落生成最长 48 个 Unicode 字素的单行指纹：

```text
[quote] 看完了，这是个挺有意思的个人情报自动化项目……
这里的三层结构为什么这样拆？
```

模型已经持有完整原回复，短指纹只负责定位。不得再次附上全文。

### 冷路径：原回复位于上下文压缩之前

如果引用源位于最近一次 compaction divider 之前，生成最长 256 个 Unicode 字素的确定性首尾摘录：前部最多 160 个字素，尾部最多 96 个字素，中间使用一个省略号连接。

```text
[quote:excerpt] 看完了，这是个挺有意思的个人情报自动化项目……（中间省略）……这些内容最终会形成可追溯的 Wiki。
这里的三层结构为什么这样拆？
```

冷路径只在完整原回复可能已经不在模型上下文时增加信息。摘录不调用模型总结，避免额外请求、延迟和语义漂移。

### 文本规范化

- 只读取最终回答正文；
- 去掉首尾空白，将连续空白和换行压成单个空格；
- 不携带 Markdown 装饰、thinking、工具结果、文件内容或耗时；
- 空正文不提供引用按钮；
- 缩略和截断按 Unicode 字素处理，避免截断组合字符或表情；
- 发送标记固定为 `[quote]` 和 `[quote:excerpt]`，不随界面语言变化。

### Token 与缓存不变量

1. 热路径引用内容不超过 48 个字素，冷路径不超过 256 个字素；模型分词因 Provider 而异，因此以字符边界而非虚构的固定 token 数量验收。
2. 引用只改变当前用户消息，不改写任何历史消息。
3. 不给历史 assistant 消息增加标签或包裹层。修改旧消息会让该点之后的 provider prompt cache 失效，引用越早，额外成本越高。
4. 不把全文复制进草稿、系统提示词或新的隐藏消息。
5. 不调用模型生成引用摘要。
6. 发送失败时保留正文和引用 chip，重试不得重复添加引用标记。

## 数据与状态

第一阶段的浏览器草稿状态保持最小：

```ts
type QuoteDraft = {
  turnId: string;
  fingerprint: string;
  fallbackExcerpt: string;
  beforeCompaction: boolean;
};
```

- `turnId` 只用于当前 WebUI 定位和校验，不发送给模型；
- `fingerprint` 用于热路径标记和 chip 缩略文字；
- `fallbackExcerpt` 只在冷路径发送；
- `beforeCompaction` 在选择引用时，根据引用源与最近 compaction divider 的相对位置确定；
- 状态使用会话 ID 分区，与现有草稿生命周期一致；
- 发送成功或用户移除引用后清理；发送失败保留。

引用标记是普通文本的兼容信封。它让 pi JSONL、CLI、导出和未适配客户端保持可读，同时让 WebUI 可以恢复只读 chip。只有在普通文本无法满足已验证需求时，才增加 `quote_ref` 协议字段。

## 实现边界

### 冻结版 WebUI 适配层

目标实现修改：

```text
webui/adapter/model-config/src/model-config.js
webui/adapter/pi-code-brand.css
webui/adapter/model-config/dist/model-config.js
webui/dist/model-config.js
webui/dist/pi-code-brand.css
```

适配脚本负责：

- 在复制按钮右侧幂等注入引用按钮；
- 从连续 assistant 回复节点提取最终正文；
- 维护会话级 `QuoteDraft`；
- 在附件区域注入、更新和移除引用 chip；
- 提交前把引用标记与正文组合成发送文本；
- 将已发送用户消息开头的引用标记折叠成只读 chip；
- 编辑排队消息时解析引用标记，恢复 chip 与纯正文。

不得通过覆盖 `window.fetch` 修改请求，也不得直接修改带哈希的官方 bundle。适配逻辑继续集中在可重复构建的 adapter 源文件中。

### 服务端与 pi agent

第一阶段不修改 `server/` 和 pi agent：现有 `/prompts` 文本链路足以发送压缩标记。服务端仍将用户文本交给 `AgentSession.prompt()`，会话格式不增加 Pi Code 私有消息类型。

### legacy `webapp/`

第一阶段不重复实现 legacy `webapp/`。它不是 8765 默认页面，同时维护两套实现会扩大漂移面。只有在以下任一条件出现时再补 Vue 原生实现：

- `webapp/` 恢复为实际发布载体；
- 官方 WebUI 提供稳定的消息操作或 composer 插槽；
- adapter 无法可靠覆盖排队、编辑或草稿恢复。

## 分阶段开发

### 第一阶段：单条引用闭环

用户价值：引用当前分支中的一条已完成回复，输入区只显示 chip；模型通过短指纹或有界摘录理解指向。

开发内容：

1. 验证点击发送和 Enter 发送都能在不覆盖 `window.fetch`、不显示中间文本的前提下同步组合引用标记；验证失败立即执行本文的停止条件；
2. 定义规范化、指纹、首尾摘录、序列化和解析函数；
3. 在复制按钮右侧注入引用按钮；
4. 复用附件区域布局显示单条可删除 chip；
5. 保存会话级引用草稿；
6. 热路径使用 `[quote]`，compaction 之前的冷路径使用 `[quote:excerpt]`；
7. 发送后的用户消息折叠显示引用 chip；
8. 同步 adapter 两处构建产物和品牌样式产物。

第一阶段验收后暂停开发，由用户确认按钮位置、chip 密度、缩略长度和模型理解是否达标。

### 第二阶段：排队、编辑与稳定性

启动条件：第一阶段通过用户验收，且引用需要覆盖排队或编辑流程。

开发内容：

1. 排队消息携带引用标记；
2. 编辑排队消息时还原 chip 和纯正文；
3. 切换会话、刷新页面和发送失败后恢复正确状态；
4. 引用源失效时显示错误态并阻止带错误引用发送；
5. 覆盖连续快速点击、重复提交和官方 WebUI 重挂载。

### 第三阶段：按证据升级协议

仅在出现以下真实需求时评估结构化 `quote_ref`：

- 多条引用；
- 刷新或跨客户端后精确回跳原消息；
- 引用关系需要进入导出或外部 API；
- 短指纹在重复回复中无法稳定定位；
- adapter 的提交编排无法可靠覆盖官方 WebUI 更新。

升级时仍以 pi `SessionEntry.id` 为引用源，不复制全文，不另建会话消息数据库。结构化协议必须同时定义旧文本标记迁移、CLI 降级显示、compaction 行为和导出语义。

## 验收标准

### 自动验证

- adapter 源文件、adapter 构建快照和实际服务产物保持一致；
- 重复执行 MutationObserver 刷新不会注入多个引用按钮或 chip；
- 48 字素指纹与 256 字素首尾摘录边界稳定；
- 含换行、代码块、组合字符和表情的回复可以安全规范化；
- 序列化与解析可以往返，重复提交不会叠加标记；
- 引用提取不包含 thinking、工具结果和耗时；
- 原有复制、从此处分叉、附件和发送行为不变。

### 页面验收

1. 引用按钮出现在复制右侧，浅色、深色、窄窗口和触摸设备下均可用；
2. 点击后只出现引用 chip，textarea 中看不到引用原文或内部标记；
3. chip 图标与文件不同，缩略文字单行省略，移除按钮可用；
4. 已有草稿、文件附件和图片附件不丢失；
5. 发送请求不包含完整原回复；
6. Agent 能正确回答针对被引用回复的问题；
7. 发送后用户消息以引用 chip 加正文显示；
8. 发送失败后引用和正文仍在，重试只产生一个引用标记；
9. 复制与从此处分叉按钮顺序、提示和行为无回归。

### 上下文验收

- 热路径发送文本中引用载荷不超过 48 个字素；
- 冷路径不超过 256 个字素；
- provider 请求中的历史消息内容与未引用时逐字一致；
- 引用不会触发额外模型请求；
- 不在浏览器存储完整原回复，只保存有界指纹和首尾摘录。

## 风险与停止条件

- 如果 adapter 无法在不显示中间文本、不污染输入历史的情况下稳定参与提交，停止继续叠加 DOM 补丁，转向可维护 Vue 源码或最小协议扩展。
- 如果短指纹在人工验收中频繁指错回复，先增加“划选片段引用”，不直接扩大默认摘录长度。
- 如果官方 WebUI 更新改变 `.a-msg`、`.a-msg-ft`、`.a-cpbtn`、composer 或附件 DOM，重新核对选择器和发送时序后再同步快照。
- 如果冷路径仍不足以回答，允许用户选择具体片段；不得默认恢复整条回复复制。
- 如果结构化协议没有第二个真实消费者，保持文本兼容信封，不建设通用引用平台。
